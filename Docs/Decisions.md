# JJMatch Decisions

## `Exact` removed from `JJValueMatchingMode`; identical values always match — 2026-10-12

The user compared `{"name":"Ali","age":30,…}` with `{"Name":"ali","age":30,…}` in the playground under `ValueMode = Normalized` and got a `ValueMismatch` for `30` against `30`: `Normalized` decides strings only, and `Exact` was a flag the caller had to add. The user decided that identity is logic that must always apply and asked for the `Exact` member to be removed altogether, over the alternative of keeping the member and implying it. Identity is now unconditional: `ValueMatcher.MatchValues` accepts identical primitives under every mode before testing any flag, and `ComparisonCache` treats every decodable primitive as identical to itself, so it no longer takes the value mode. `JJValueMatchingMode` is `None = 0`, `Normalized = 1`, `Fuzzy = 2`, `Numeric = 4`: the remaining flags were renumbered so that no bit is left unused. `None` now means no relaxation, identical values only; it is the default of `JJMatchSettings.ValueMode` and of an unset mode, and `JJMatcher.Match` no longer rejects it. This supersedes "Exact is not implicit when a caller chooses other value flags", "`None` matches nothing" and the numbering of 2026-10-11 below.

This is a breaking change to the public enum: code naming `JJValueMatchingMode.Exact` no longer compiles, a `JJSetting.json` holding `"Exact"` is rejected by `FromJson` as an unknown member, and stored numeric values change. The package has not been published, so no released consumer is affected. Nothing that matched before stops matching; only mismatches between identical values under a single relaxed rule disappear. `JJPropertyNameMatchingMode.Exact` is a different enum and is unchanged. Guide row D (Strict + Numeric) moves from 35 with 12 value mismatches to 55 with 8; rows E and F are unchanged because the example holds no identical number or Boolean that only `Exact` accepted. The tests that pinned the old separation were rewritten to pin the new rule (`None_accepts_identical_values_only`, identical numbers, Booleans and nulls matching under `Normalized`, `Fuzzy` and `Numeric` alone, the enum shape), the public `None` rejection assertion was removed, and `Value_rules_work_through_the_public_api` additionally asserts that `guideScenario` matches itself under each single rule. The playground lost its `Exact` checkbox.

## Weighted scoring — 2026-10-12

The user asked for a weighted scoring system in which each kind of mismatch has an importance weight from 1 to 10, configurable through `JJMatchSettings` with sensible defaults, with the current score kept as the default behavior, `IsMatch` and difference reporting untouched, and a configuration that is always present and never null. That request is the documented requirement guideline 6 asks for, and it authorizes the one new public class and enum.

- **Configuration:** `JJMatchSettings.Scoring` holds a `JJScoringSettings` (`Options/`), initialized by the settings object itself; the setter rejects null with `ArgumentNullException`, so the configuration is never absent. `JJScoringSettings` has `Mode` of the new enum `JJScoringMode` (`Standard = 0`, the default, and `Weighted = 1`), the constants `MinWeight = 1` and `MaxWeight = 10`, and one weight per public `JJDifferenceKind`: `TypeMismatchWeight` 10, `MissingWeight` 8, `ValueMismatchWeight` 6 and `AddedWeight` 3 by default, reasoned as: a wrong type breaks the shape a consumer relies on and nothing below it is compared, missing content was expected, a wrong value keeps the shape, and extra content leaves everything expected in place. Weights are keyed by the public kind rather than the internal `StructureMismatchType`, because the public kind is what a consumer sees in `Differences` and the earlier decision reserved finer public categories for a `JJDifferenceKind` decision; the duplicate-count category takes the weight of the side it is reported on. `Snapshot` copies and validates the configuration with the rest of the settings (weights outside 1 to 10 and an undefined mode throw `ArgumentOutOfRangeException`, under `Standard` too), so a caller's later change cannot reach a running comparison. `FromJson` reads a nested `Scoring` object with the same naming rules.
- **Formula:** `Weighted` is a weighted Sørensen–Dice over the same maximum correspondence: a matched node weighs `MaxWeight` on each side and an unmatched node weighs the weight of the kind of the difference reported above it, so `Score = 100 × 20M / (20M + Σ w(d) × n(d))`, where `n(d)` is the subtree size the difference accounts for, counted as the denominator counts (`CountNodes`, shape-reduced under StructureOnly). Every unmatched node lies under exactly one difference, so `Σ n(d) = L + R − 2M` and nothing is counted twice; with every weight at 10 the quotient is the Standard one as the same rational number, computed by one correctly rounded division, so the modes then agree bit for bit. The baseline of 10 for a matched node was chosen over the largest configured weight so that the scale is absolute and predictable: 10 means the Standard cost, lower weights discount, and a weighted score is never below the standard one. The alternative of a baseline of 1, under which weights would amplify, crushed every score (the guide pair fell from 50 to 14) and was rejected. `StructuralMatchPercentage` applies the same weights to the structure-only pass; `ValueMatchPercentage` is the `Score` as before. Both passes now run before either score is computed so that the weighted computation, which reads subtree sizes through the shared cache, cannot affect them.
- **`JJDifference.ScoreWeight`:** on seeing the playground's difference table the user asked for a `ScoreWeight` property on each difference. It is the weight the score applied to that difference, from 1 to 10: the configured weight of its `Kind` under `Weighted`, and `MaxWeight` under `Standard`, where every difference counts fully. The user chose this over the difference's share of the lost score and over 0 standing for Standard mode. It is set by the matcher, read-only, and shown as a column in the playground table.
- **Direction:** swapping the documents turns `Missing` into `Added`, so the weighted score is symmetric only when the two weights are equal or are swapped with the documents. Accepted as the point of distinct weights: the left document is the expected one. The alignment is still the unit-weight maximum, so a pairing leaving a lighter weighted mass unmatched is not sought; recorded in `Match.md`.
- **Tests and docs:** `JJMatcherIntegrationTests` pins the defaults and the non-null guarantee, hand-computed weighted scores on `nested`, `guideScenario`, `basic`, `surplus` and the type-mismatched roots, the bit-for-bit agreement with Standard at weight 10 across every array mode, option set and `publicApi` pair, the unchanged `IsMatch` and differences, the discount-only and swapped-weight symmetry properties, and the validation. No fixture changed. `Scoring.md` defines the mode, `Guide.md` shows the configurations W, X and Y on the example pair, and guideline 6 names the mode as the documented exception. `FromJson` has no test, as before, and the playground was not changed. Validation: Release build without errors; 201 tests pass on .NET 10.0.11 exercising the net8.0 assembly; the net8.0 test target was not run because no .NET 8 runtime is installed locally.

## Unbounded depth and elapsed time in the result — 2026-10-12

The user typed a `MaxDepth` of 964 into the playground and hit `ArgumentOutOfRangeException`, and decided the depth must not be capped at all. `Snapshot` now rejects only a `MaxDepth` below 1; any larger value is passed to the parser unchanged. The stack-safety limitation below stands and is now the caller's responsibility: the traversal, the matching and the location walk each recurse once per level, so a document deep enough for the configured depth can overflow the stack, which cannot be caught. The default of 64 is unchanged, the playground input lost its upper bound, and the former cap test now asserts that 0 throws and that 129 and `int.MaxValue` are accepted. The user also asked for the time the call took: `JJMatchResult.ElapsedMilliseconds` is added, a `double` measured with `Stopwatch` from the first argument check to the result's construction, so it covers validation, parsing, both comparisons and difference reporting. It is wall-clock time, so it varies between runs; the tests only assert that it is not negative, and the playground shows it with the scores. The package has not been published, so no released consumer is affected.

## Configurable fuzzy threshold — 2026-10-12

The user asked for the `Fuzzy` threshold to be a setting. `JJMatchSettings.FuzzyThreshold` is added, a `double` from 0 to 1: the least similarity `Fuzzy` accepts, where similarity is one minus the edits divided by the length of the longer folded text. The threshold has three sources, each overriding the one before, as the user specified: the constant `ValueMatcher.DefaultFuzzyThreshold` (0.8, which replaces `FuzzyUnitsPerEdit = 5` and keeps the same rule, one edit for every five units), the setting, which initializes from the constant and which `JJMatcher.Match` passes down, and the `fuzzyThreshold` parameter of `ValueMatcher.MatchValues` and the internal `StructureMatcher.Match`, which decides whenever it is given. Both parameters are trailing and optional, so every existing internal caller, the legacy overload and the benchmarks are unchanged. The allowance is `length − ceiling(threshold × length)`, the units that may be lost, rather than `floor((1 − threshold) × length)`: `1 − 0.8` is below `0.2` in binary and the floor would reject `"Smith"` against `"Smyth"`, while `0.8 × 5` rounds to exactly 4, so a threshold written in decimal keeps its exact boundary. `Snapshot` rejects a value outside 0 to 1 and NaN with `ArgumentOutOfRangeException`. At 1 `Fuzzy` accepts what `Normalized` accepts; at 0 any two strings are equal, which uncovered that the banded distance returned above the bound for an empty text (the band held no cell, so the row minimum started above the bound); the minimum now starts from column zero, which the early-exit argument already covered. `ValueMatcherTests` pins the default, both boundaries, 0 and 1 and that numbers stay undecided; `JJMatcherIntegrationTests` covers the setting through the public API and its validation, all from the existing `fuzzyValues` pairs. The playground gained a `FuzzyThreshold` number input beside the value rules, in its C# snippet and in the `JJSetting.json` preview. The default of 0.8 is unchanged, so no result moves unless the setting is used; whether the default should scale for short texts remains open.

## Settings from JSON and a configurable depth in the playground — 2026-10-12

The user hit `JsonReaderException: The maximum configured depth of 64 has been exceeded` in the playground, which never set `MaxDepth`, and asked for a settings file holding the limit, a depth input in the playground, and a copyable preview of that file. `JJMatchSettings.FromJson(string)` is added, a static method on the existing class and the only new public member: it reads a JSON object whose properties are named like the settings properties (case ignored), with modes as member names, value rules joined by `|` or `,`, and limits as integers; omitted properties keep their defaults, and an unknown name, a wrong type or a non-object root throws `ArgumentException`. The result goes through `Snapshot`, so a file is validated when loaded exactly as settings passed to `Match` are. Reading the file is left to the caller (`File.ReadAllText`), so the library stays free of file system access and the Blazor playground can show the same file. The playground gains a `MaxDepth` number input (1 to 128), puts the value in its C# snippet, and shows the equivalent `JJSetting.json` beside it, each with a Copy button backed by the browser clipboard; without clipboard access both snippets still select whole on click. The depth cap of 128 is unchanged: the traversal still recurses once per level and the stack-safety limitation below stands. No test was added; the fixture rule would require a settings object in `Left.json` and both TXT fixtures, which the user may want to decide on.

## Property name matching mode — 2026-10-12

`JJMatchSettings.PropertyNameMode` is added, of the new enum `JJPropertyNameMatchingMode` (`Exact = 0`, the default, and `Normalized = 1`). The user found that `name` against `Name` in an LLM response was reported as a missing and an added property under every setting, which was the documented behavior: every value rule relaxes values only. Names are a separate axis from values, so they get a separate setting with an enum of their own rather than a reuse of `JJValueMatchingMode`, whose `Numeric` makes no sense for names and whose flags combine by OR where the name rules form a hierarchy.

- **Rule:** under `Normalized` a name is keyed by `ValueMatcher.Normalize` (trimmed, NFC) and keys are compared with `OrdinalIgnoreCase`, the same rule as `Normalized` string values; `postalCode` and `postal_code` stay different. The rule is structural: it decides which properties pair under every option, so it moves `StructuralMatchPercentage` too, and a pair of names it accepts is a plain match with no difference reported, as a pair of `Normalized` values is. Names of one object that fold together become a duplicate-name group, assigned by the existing rules; the facade's occurrence suffixes still follow exact names, so such properties keep distinct paths under their own spelling.
- **Implementation:** `NameIndex` keys properties under the rule and exposes `Contains`; `CanPair` tests shared names through it; the `ComparisonCache` interns names in a table of its own under the rule, so identities, StructureOnly shape deduplication and `CountNodes` all follow it, while value texts stay ordinal. The internal `Match` and the cache take the mode as a trailing optional parameter, so the legacy overload, the benchmarks and the existing tests are unchanged. A `Normalized` call normalizes every name once per object index; no other cost is added.
- **`Fuzzy` names left out for now:** names are short, so one edit per five units either never fires (`id`, `age`) or pairs genuinely different names (`tag` and `tags`), and fuzzy similarity is not transitive, so pairing could no longer group by key and would need a whole-object assignment with `MaxAssignmentSize` applied to ordinary objects. Adding it later is additive; removing it later would break consumers.
- **Fixtures and tests:** both fixtures gained `publicApi.propertyNames` (names differing in case, outer white space and Unicode form, one name that stays different, and an array whose element objects fold to one shape), the Stringified fixtures were regenerated, and `JJMatcherIntegrationTests` covers the setting, its validation and the symmetry sweep under both modes; `core.caseVariants` against `publicApi.basic` pins the duplicate-group behavior. The playground gained the setting. The package has not been published, so no released consumer is affected.

## Stringified JSON is decoded automatically — 2026-10-12

`JJMatchSettings.ParseStringifiedJson` is removed. A root that is a JSON string whose content, after leading JSON white space, starts with `{` or `[` and parses as JSON is decoded, one layer only; the parsed document replaces the string. Every other string root stays a literal string: one holding other text (`"hello"`, `"123"`), one whose content does not parse (`"{"`), and one that cannot be decoded as Unicode text (a lone surrogate). The user chose this over decoding any valid JSON scalar (`"123"` would become the number `123`) and over decoding every string root (plain string roots could no longer be compared). Strings nested inside a document stay literal as before. The opt-in existed to avoid reinterpreting an ordinary string; restricting decoding to objects and arrays covers that without a setting. The package has not been published, so no released consumer is affected.

## Unused mismatch categories removed — 2026-10-12

`StructureMismatchType` had seven members that nothing produced: `ArrayLengthMismatch`, `ArrayElementShapeCountMismatch`, `NullabilityMismatch`, `ContainerKindMismatch`, `ScalarContainerMismatch`, `PropertyNameCaseMismatch` and `PropertyNameNormalizationMismatch`. They were added on 2026-10-12 with the `Fuzzy` work as documentation comments only, and the cleanup entry below kept them deliberately. They were then implemented in full as reporting-only categories, with tests, a fixture section, documentation and before/after benchmarks, and assessed: the public result was byte-identical, because `JJDifferenceKind` collapses every internal category to Missing, Added, TypeMismatch or ValueMismatch, and nothing outside the matcher reads the internal category except the facade; three of the categories were derivable in one line from the two snapshots a `JJDifference` already carries; each needed a precedence rule to invent; and the lazily built name sets cost a few percent of allocation on documents with many unpaired properties. On that assessment the user chose to remove the seven members outright rather than keep vocabulary nobody reads. The implementation, its tests and the fixture section were reverted, and the enum holds the six categories the matcher produces plus `ValueMismatch`. Two of the removed names would have corrected imprecise naming: a Strict element beyond the other array's length and an Unordered element the assignment leaves over are both reported as `MissingArrayElementShape`/`ExtraArrayElementShape`, whatever shape the other array holds. That imprecision is accepted and noted in `Match.md`. If a public "renamed property" or finer type kind is ever wanted, it is a `JJDifferenceKind` decision, to be made together with the internal category.

## Public API completion — 2026-10-12 (current decisions)

The user's request to complete the public NuGet API explicitly authorizes implementation, architecture, scoring and behavioral decisions. It supersedes earlier deferrals below; no additional architectural approval is required for this work.

- **One usable entry point:** `JJMatcher.Match(string, string, JJMatchOptions?, JJMatchSettings?, CancellationToken)` returns an immutable `JJMatchResult` exposing `IsMatch`, `Score` and a read-only `Differences` list. This replaces the empty void stub. Existing source calls that ignore the return remain valid; already compiled consumers must rebuild because the public signature changed. There is no `Compare` or `JJMatchWeights` API.
- **Defaults:** exact primitive values and Strict arrays, with object property order ignored. The zero enum member remains StructureOnly for numeric compatibility, but new settings explicitly select Strict. This is the first implemented public comparison default. The two-argument internal StructureMatcher retains its old structural shape semantics and tests.
- **Scoring:** Sørensen–Dice over maximum permitted node correspondence, `200M/(L+R)`, with unit weights including containers. [Scoring.md](Scoring.md) gives the research, denominator, constraints, endpoint proof, examples and limitations. No arbitrary component averages or domain weights. Score 100, IsMatch true and no differences are equivalent.
- **Reuse:** the existing matcher now supports Strict, Unordered and StructureOnly arrays. It delegates leaves to ValueMatcher; parsing, scoring and public snapshots belong to JJMatcher. Structural identity/deduplication never uses fuzzy equality. StructureOnly ignores all primitive values below arrays, including nested object properties, and counts each structural shape once.
- **Options:** All (zero), both scored flags, or neither scored flag compare structure and values. StructuralMatching alone ignores values. ValueMatching alone includes necessary structure but omits the separate structural diagnostic. ArrayMatching and DifferenceReporting remain compatibility flags; arrays and differences are always handled. WeightedScoring and unimplemented value flags explicitly throw. Exact is not implicit when a caller chooses other value flags; use Exact with Normalized/Fuzzy/Numeric for mixed JSON.
- **Results:** MatchPercentage aliases Score. StructuralMatchPercentage is an independent structural diagnostic under the same array policy. ValueMatchPercentage is the value-aware document score, not an independent component. Snapshots are cloned before source documents are disposed. Missing differs from present JSON null. Unmatched or type-mismatched subtrees produce one difference each.
- **Locations:** original array indices and one-based duplicate-property suffixes (`$.entry#2.value`) identify occurrences. Escaping reuses the existing path formatter. Left and right locations are separate; tie resolution is deterministic but left-oriented. Locations are diagnostic, not executable JSONPath or JSON Patch. A second traversal maps original tree nodes to source elements only when differences exist.
- **Inputs:** all JSON roots are accepted. Outer stringified JSON was decoded exactly once only with ParseStringifiedJson, and an outer string with undecodable Unicode escapes threw JsonException; both are superseded by the automatic decoding entry above. Nested strings stay literal. Invalid text/comments/trailing commas/depth overflow throw JsonException, null arguments throw ArgumentNullException. Existing malformed-surrogate traversal behavior is retained; raw snapshot access remains available even when BCL string decoding rejects a surrogate escape.
- **Resources:** settings are copied per call. Defaults: input length 1,000,000 UTF-16 units per side, depth 64, total nodes 100,000, assignment-group size 128 per side, work allowance 10,000,000. Hard caps: nodes 1,000,000, group size 256; depth had a cap of 128 until 2026-10-12 and is now unbounded. These bound recursion and count/cost arithmetic; limit exhaustion throws, never returns approximate results. Cancellation is cooperative. Shape work, speculative pairs, solver iterations and expensive value work share one budget. Object eligibility uses a name set to avoid an unbudgeted quadratic name scan. No end-to-end performance improvement is claimed.
- **Fixtures and coverage:** existing core/stress content is preserved; publicApi sections add needed consumer scenarios, including malformed text stored as a fixture string. The TXT inputs remain exact stringifications. The former scoring skip is replaced by active end-to-end coverage. The historical excluded JJMatcherTests remains excluded: it targets the abandoned Compare/weights design and arbitrary percentages; no previously active tests are removed or weakened.
- **Distribution:** Guide.md is the NuGet package readme, and root README is also included. Targets remain netstandard2.0 and net8.0. No publish, push or commit is authorized by this task.

## Performance optimization — 2026-10-12

The request to optimize the library authorized algorithmic changes that preserve every result, score, difference, path, error and public signature. Each change was measured against the unchanged implementation (the end-to-end benchmarks in `benchmarks/JJMatch.Benchmarks/JJMatcherBenchmarks.cs`, the existing component benchmarks, and a stopwatch harness outside the repository); only changes with a measured benefit were kept.

- **Per-call cache (`ComparisonCache`):** one per public call, shared by `CountNodes` and both matching passes, and created by any internal `Match` call that is not given one. It gives each indexed subtree an exact identity under the array mode: an interned canonical key of its kind, its property names and the identities of its children (ordered for Strict arrays, sorted for Unordered, distinct for StructureOnly), with a second identity that also carries the primitive values a selected rule accepts as identical to themselves (every decodable primitive under `Exact`, strings under `Normalized` and `Fuzzy`, numbers under `Numeric`; an undecodable string is identical to nothing). Identities replace the former shape texts, which were rebuilt for every candidate pair of every group and for every nested array, and whose total length grew with the square of the nesting depth. Equal identities are a proof, never a hash: a pair of identical subtrees is matched whole without being walked, at any depth, and unequal identities only mean the pair is compared as before. Only group members and their descendants are ever indexed, so a document without unordered arrays, duplicate names or StructureOnly arrays pays nothing for it; primitives are never stored.
- **Count-only speculation:** the candidates of a group are compared for their matched count alone, without difference lists or formatted paths; the pairs the assignment takes are compared once more to report their differences. The former version built a difference list with formatted paths for every candidate and kept all of them until the group was assigned, which was most of the time and memory of unordered and duplicate-name matching. The tie rule now reads "no differences" as "every node of both subtrees matched", which is equivalent; the exhaustive solver test keeps its per-cell seam.
- **Assignment:** the Hungarian solver reads a cost matrix computed once instead of recomputing each cell on every visit, and reuses its slack and visited arrays across rows. One element on each side of an array is paired directly, without identities or a solver, when it may be paired.
- **Object pairing:** each object's properties are indexed by name once (`NameIndex`: the last index of each name and each property's previous namesake), partners and paired flags are tracked by index instead of by dictionary and set, and the index is kept for group members, which are compared once per candidate.
- **Value rules:** `Fuzzy` accepts equal folded texts without a table, fills only the band of the table within the allowed edits of the diagonal, and reuses its three rows across the pairs of a call; the normalized and folded texts of a string are kept across the candidates of a group. The banded table returns the exact distance whenever it is within the limit and a value above it otherwise, which is all the rule reads.
- **Public facade:** the structural diagnostic pass is skipped when the value-aware pass found no difference, because a full value match is a full structural match and no count can exceed the total; otherwise both passes share the cache. Locating differences visits only the containers above a referenced node and formats only their paths, instead of building a path and an entry for every node of both documents.
- **Not kept:** a memo of candidate matched counts keyed by node pair, meant to spare the reporting pass from counting nested groups again, was measured slower on flat and nested input alike and removed.
- **Unchanged by decision:** the tree and its lists and strings (no trimming, pooling or interning, per the earlier measurements), the `Traverse` fallback for lone surrogates, parsing, and the n² candidate counts that the maximum assignment needs. The work budget is spent on the work actually done, so a call consumes less of `MaxWork` than before for the same input; limits still fail the operation rather than degrading it, and the limit tests are unchanged.

## Decisions

- **Test fixtures:** all JSON test input comes from `TestData/ComplexJson/Left.json` and `Right.json`. Tests select sections of them; no inline or generated JSON and no other fixture files, apart from the Stringified fixtures below.
- **Folders by role and concern:** public enums a caller passes in live in `Options/`, public result types in `Models/`, and internal code in `Internal/JsonStructure/` and `Internal/Matching/`; tests mirror the two concern folders. Every source file stays in the `JJMatch` namespace. This replaces the earlier layout of one folder per function under `Infrastructure/`, each with a `README.md`: those documents are now `Docs/ExtractPropertyPaths.md`, `Docs/Traverse.md` and `Docs/Match.md`, and `src/` holds code only. The test files and classes were renamed to `ExtractorTests`, `TraverserTests` and `StructureMatcherTests`.
- **Scoring:** not implemented until explicitly requested.
- **`JsonStructureTraverser` stays a separate class** from `JsonStructureExtractor`; neither was merged or split for the folder layout.
- **`JJMatcher` stays at the project root:** it is the public entry point, not an infrastructure function.
- **No test for invalid JSON at the extractor level:** `ExtractPropertyPaths` takes a parsed `JsonElement`, so invalid input is rejected by `JsonDocument.Parse` before it is reached.
- **A string `Value` is decoded or absent, never raw, and lone surrogate escapes are decoded as written:** the parser accepts a lone surrogate escape (`"\uD800"`, `"\uDC00"`) in a name or a value, but `JsonProperty.Name` and `JsonElement.GetString` reject it when they decode the text. `Traverse` then decodes the raw text itself, turning each `\u` escape into the UTF-16 unit it names, so the name or value is kept exactly: a lone high surrogate, a lone low one and a valid pair are three different strings, and a lone one inside other text stays in place. Names that decode normally take the normal path, so valid documents are not affected and cost nothing more. The alternative, rejecting such input, was not taken: the parser has accepted it, and a name cannot be left out. A string the parser accepted whose UTF-8 bytes are invalid (possible only when parsing bytes, never a .NET string) cannot be represented and keeps its `String` node with `Value` `null`; such a property name makes `Traverse` throw `InvalidOperationException`. Raw JSON text is never stored as a `Value`.
- **The fallback reads names from the object's bytes, not from `GetRawText`:** `GetRawText` transcodes the whole object to a .NET string and throws for invalid UTF-8 in any string below it, so an object holding a lone surrogate name and, anywhere under it, a string value with invalid UTF-8 made `Traverse` throw, although such a value alone only loses its `Value`. Only the names are needed, so they are now read with a `Utf8JsonReader` over the element's own UTF-8 bytes. `System.Text.Json` 8 has no public accessor for those bytes (`JsonMarshal.GetRawUtf8Value` arrived in version 9), so the reader is obtained through `JsonSerializer.Deserialize(JsonElement, JsonTypeInfo<T>)`, which hands a converter a reader over them: a private nested `RawNamesConverter` collects the names. Its `JsonTypeInfo` is built with `JsonMetadataServices.CreateValueInfo` and an empty resolver, so no reflection-based serialization is involved, and it is created only when the fallback first runs. Names are decoded strictly, so a name with invalid UTF-8 still throws `InvalidOperationException` instead of being silently replaced by U+FFFD. Checked against the `System.Text.Json` 8.0.5 assemblies for both the `netstandard2.0` and the `net8.0` build, and on .NET 10.
- **Empty containers share the empty child list:** an empty object or array holds `Array.Empty<JsonStructureNode>()`, like a primitive.
- **No list trimming or name pooling:** both were measured in a one-off run outside the repository and left out. Trimming child lists retained about 3% less and allocated about 8% more. Pooling property names retained 8% less on the fixtures while allocating 29% more, and 23% less on an array of 1,000 same-shaped objects at almost no allocation cost; it is worth revisiting only if large repetitive documents become a real use case.
- **No inline-JSON exception any more:** `Undecodable_string_value_does_not_stop_extraction` parsed a small literal holding a lone surrogate escape because such a string could not live in the fixtures without breaking every whole-document test. Since lone surrogates are decoded, both fixtures hold a `loneSurrogates` section (a lone high surrogate name declared twice, a lone low one, a valid pair, the same names nested under an object and an array, and the same escapes as values) and the test was migrated to it. No test uses inline JSON.
- **Invalid UTF-8 tests damage the fixtures' own bytes in memory:** invalid UTF-8 cannot be written in a text fixture, and reading one as text would replace it. The two `Traverse` tests for it load the bytes of `Left.json` or `Right.json`, overwrite the last byte of a few marked texts with `0xFF` and parse the bytes (`LoadWithInvalidUtf8` in `TraverserTests`). The fixture files stay the only source of JSON and nothing is added to them for it; this is the one place where a test does not parse a fixture exactly as stored.
- **Test targets:** the test project targets `net8.0` and `net10.0`. `net10.0` references the library's `net8.0` build and `net8.0` references its `netstandard2.0` build, so both shipped assemblies are executed. The workflows install the 8.0 and 10.0 runtimes.
- **Benchmarks:** `benchmarks/JJMatch.Benchmarks` measures time and allocations of `Traverse` and `ExtractPropertyPaths` over the two JSON fixtures, and of `StructureMatcher.Match` over the fixtures and over generated arrays of distinct shapes, with BenchmarkDotNet. It compiles the extraction and matching sources in directly, so the library exposes nothing for it. The generated documents exist only in the benchmark project: the fixture rule covers tests. Memory is measured there, not asserted in unit tests.
- **Two input representations:** JJMatch must eventually handle both normal JSON (an object or array) and stringified JSON (the same document serialized as an escaped JSON string, as some APIs deliver it). After parsing or normalization, both must give equivalent extraction and matching results.
- **Stringified fixtures:** `TestData/Stringified/LeftStringify.txt` and `RightStringify.txt` hold the same content as `Left.json` and `Right.json` in stringified form. They are input-format test fixtures, not hierarchical ID mapping output, and must be kept in sync with the two JSON fixtures.
- **`Traverse` builds a tree; hierarchical IDs are derived from it:** `JsonStructureTraverser.Traverse` returns a `JsonStructureNode` tree holding structure and primitive values (`PropertyName`, `ValueKind`, `Value`, `Children`) and is the only code that walks a source `JsonElement`. `ExtractPropertyPaths` projects the `Dictionary<string, List<string>>` from that tree, with the ID rules unchanged. IDs, paths, array indices and occurrence indices are not stored on nodes: an ID depends on the element the walk started from, and matching must not compare IDs anyway. Strings are stored decoded and numbers as raw text, never as `double` or `decimal`; nothing is normalized at extraction. `JsonElement` is not retained, so the tree does not depend on the `JsonDocument` lifetime. Details are in `Traverse.md`.
- **Ordering is a matching concern, not an extraction concern:** ID generation stays depth-first and in encounter order. Neither `Traverse` nor `ExtractPropertyPaths` sorts properties or takes a matching enum, and the tree keeps properties and elements in document order. The IDs are therefore order-sensitive: the same properties in a different order can be numbered differently.
- **Object property order is always ignored in structural matching**, in every mode including `Strict`. Because of the point above, matching must not compare the IDs of two separately extracted documents number by number.
- **Array element order depends on `JJArrayMatchingMode`:** it matters in `Strict`, does not matter in `Unordered`, and `StructureOnly` follows the array rules in the project README (count and order ignored). Order is ignored unless the caller explicitly selects an order-sensitive mode; `StructureOnly` is the default, as the enum's zero value. `Strict` is the only order-sensitive mode.
- **`JJMatchOptions.ArrayMatching` does not control element order:** its earlier description ("without it, arrays are compared position by position") made the absence of a flag order-sensitive, which contradicted the default above. Element order is governed by `JJArrayMatchingMode` alone. Only the documentation changed; the enum members and values are untouched.
- **Array matching needs more than the extracted dictionary:** `Dictionary<string, List<string>>` cannot reliably reconstruct array element order or element boundaries: arrays with their elements in different orders can extract identically, and arrays holding the same elements can extract differently (the `arrayElementOrder` fixture section). Future `Strict` and `Unordered` array matching must use the `JsonStructureNode` tree, which preserves element order and boundaries.
- **Structure matching is `StructureOnly` only, on the tree:** `StructureMatcher.Match` compares two `JsonStructureNode` trees and returns a `StructureMatchResult`. `Unordered` and `Strict` are not designed or implemented, and the method takes no mode. Details are in `Match.md`.
- **A full structural match means zero differences:** primitive values, object property order, array element order and repeated element shapes are ignored; any other structural difference makes the result a non-match, however similar the documents are.
- **Structural types:** `True` and `False` are one Boolean type. Every other kind matches only itself, so `null` against any other type is a type mismatch. Nothing below a type mismatch is compared.
- **One difference per unmatched subtree:** a property or element shape present on one side only is reported once, at its top. The difference holds the node, so what lies below it stays available.
- **`StructureOnly` arrays compare distinct element shapes:** elements are not merged into one shape with optional properties. An empty array holds no shape, so `[]` against a non-empty array is a difference.
- **Occurrences are paired by the best assignment of their whole group:** same-named properties and array element shapes are paired one to one so that the fewest nodes are left unmatched over the whole group, identical shapes included. Among equal assignments the one pairing the most identical shapes is taken, then the one with the most pairs, then document order decides, left side first. This replaces greedy pairing for array element shapes, document-order pairing for same-named properties, and the later rule that paired identical shapes first and assigned only the rest, which could lose nodes when two leftover objects shared no name. Among array element shapes two primitives of one type, two arrays, two objects sharing a property name or two empty objects are paired; among same-named properties every pair may be made.
- **Pairing never decides a match:** when both sides hold the same shapes, the only assignments matching every node pair identical shapes, so `IsMatch` does not depend on the assignment.
- **The pairing cost is not scoring:** it is an unweighted node count, private to `StructureMatcher`. A whole unmatched subtree weighs its size in the cost and is still reported as one difference. Scoring is free to define its own measure.
- **No assignment limit:** every group is assigned as a whole, whatever its size. An earlier version assigned only groups of up to 32 occurrences, paired larger ones greedily after pairing identical shapes first, and set an `AssignmentLimitExceeded` flag on the result to say that `MatchedCount` might then be below the maximum. The limit was removed for correctness, not performance: the benchmarks showed that comparing every pair is the whole of the cost and the assignment adds nothing measurable, so the fallback saved nothing and only made `MatchedCount` wrong above the limit. The flag, `DefaultAssignmentLimit` and the `Match` overload taking a limit are gone, and Scoring never has to handle a degraded count.
- **Two notions of matching:** *structurally equivalent* is `IsMatch`: the two structures fully match under the selected mode. *`MatchedCount`* is the number of structurally matched nodes, and it is the maximum any valid pairing could reach, so no third notion is needed.
- **`MatchedCount` is the maximum possible:** it is the greatest number of matched nodes any pairing could reach under the pairing rules, for every input. It is therefore the same when the two arguments are swapped, never exceeds the size of either side, and reaches both sizes exactly when `IsMatch` is `true`; the tests check these invariants over every section of the fixtures. The pairing cost is a 64-bit integer, but no unconditional overflow or resource bound has been established; very large counts and groups have no explicit guard.
- **Correctness before performance in this version** (the optimization above was later authorized and keeps these semantics): the priorities are, in order, correct structural matching, accurate mismatch classification and reporting, complete functional test coverage, and clear, stable result semantics. Memory allocation, execution time and algorithmic cost are not optimized now, and working algorithms are not refactored for performance alone. The benchmarks and their findings stay documented. Optimization belongs to later versions.
- **Duplicate property names are paired in any order:** the whole group is assigned by the rule above, with identical pairs preferred only among equal matched counts, pairing as many as possible; two of different types are a `TypeMismatch` and a surplus occurrence is a `DuplicatePropertyCountMismatch`. Object matching therefore has no order-sensitive case left. This replaces the earlier decision to pair them by occurrence, first with first. A consumer that keeps the last occurrence reads a different value when duplicates are swapped; that is a value difference, not a structural one.
- **Structural differences use an internal `StructureMismatchType`:** `MissingProperty`, `ExtraProperty`, `TypeMismatch`, `MissingArrayElementShape`, `ExtraArrayElementShape`, `DuplicatePropertyCountMismatch`. The public `JJDifferenceKind` was not changed, so that later scoring can tell the categories apart directly. A difference holds the mismatch type, a path and the two nodes, and no text.
- **Paths are for reporting; nodes are the reference:** `$` is the root, `[*]` any array element, and a name that is not a plain identifier is written in brackets (`$['a.b']`), with `\` and `'` escaped by a backslash so that a name cannot end the brackets early. Plain identifiers are judged as Unicode code points, so a letter outside the Basic Multilingual Plane is plain. Inside the brackets every invisible character (controls, format characters, line and paragraph separators, spaces other than U+0020, lone surrogates) is written as a JSON escape (`\n`, `\u007F`), so a path is always one printable line; visible characters, emoji included, are written as they are. The escapes are those of an RFC 9535 single-quoted name. Names on the nodes are never changed. A path does not identify a node.
- **Stringified JSON inside a document is an ordinary `String` leaf:** neither `Traverse` nor `StructureMatcher` parses string content.
- **The Stringified fixtures are copied to the test output**, so the matcher test can parse their roots as JSON strings.
- **Original value-mode design, superseded by the dated implementation and flag decisions below:** `Exact` (`0`, the default), `Normalized`, `Fuzzy`, `Token`, `Numeric`, `TypeCoerced`, `Contains` and `Pattern` (values 1 to 64). They exist because LLM output is often right in substance while differing in spelling, casing, word order or data type. They were first added to `JJMatchOptions` as values 32 to 2048 and then moved out, because they are a policy for comparing two leaf values rather than a feature of the matcher: they only apply when `ValueMatching` is on, they mirror how `JJArrayMatchingMode` already holds the array policy, several will need parameters later, and keeping them in `JJMatchOptions` forced the exception that `All` did not imply them. `All` now genuinely enables every option, and `Exact` is the zero value like `StructureOnly`. No comparison logic, similarity measure or threshold exists, so the scoring rule is untouched. Semantic (embedding-based) matching was left out: it needs an external model.
- **`Normalized` value matching is implemented, as the internal `ValueMatcher.MatchValues`:** it takes two `JsonStructureNode`s and a `JJValueMatchingMode` and returns whether their values are equal. Each flag is one rule and a pair is equal when any set rule holds, so modes combine with `|`; only `Normalized` has a rule yet. `Normalized` applies to two strings only: each value is trimmed of leading and trailing white space (`char.IsWhiteSpace`) and put into Unicode NFC, and the two texts are compared with `OrdinalIgnoreCase`, so the current culture plays no part (`"i"` matches `"I"` under a Turkish culture, and `İ` and `ı` match neither). Internal white space and punctuation are kept, so the enum's earlier wording that repeated white space is ignored was corrected; nothing is coerced, so `"123"` never matches `123` and `"true"` never matches `true`; an empty string matches a white-space-only one; a string holding a lone surrogate is only trimmed, because it is not Unicode text and `string.Normalize` rejects it; a string without a `Value` matches nothing. Values on the nodes are never changed, and `Normalize` returns its input when nothing needs to change. `Normalized` says nothing about non-string values: `Exact` decides them (below), so with only `Normalized` set two equal numbers are not equal. `StructureMatcher` does not call it and nothing public reaches it; no scoring and no value-based array pairing exist. Details are in `MatchValues.md`.
- **`JJValueMatchingMode` has `None = 0` and every mode is its own flag:** `Exact` was `0`, so `Exact | Normalized` was indistinguishable from `Normalized` and a caller could never ask for exact *and* normalized equality. On 2026-10-11 `None = 0` was introduced and the modes renumbered as powers of two in the existing order: `Exact` `1`, `Normalized` `2`, `Fuzzy` `4`, `Token` `8`, `Numeric` `16`, `TypeCoerced` `32`, `Contains` `64`, `Pattern` `128`. The member names are unchanged. This is a breaking change for any consumer that stored the numeric values or compared against `0` for `Exact`; the names serialize the same. No workaround was added: the package is `0.1.0`, no public method takes the mode yet, and nothing in this repository stores it. The default is no longer implicit: an unset `JJValueMatchingMode` is `None`, which compares nothing, so whatever public API first accepts the mode must default it to `Exact` explicitly, and the former rule to test `Exact` with `==` is gone, `HasFlag` works for every mode. `ValueMatcher.MatchValues` is unchanged in logic: it tests each flag for its rule, and a flag without a rule (`Exact` and the rest, not yet implemented at the time) or `None` never makes a pair equal.
- **`Exact` value matching is implemented, as a second rule of `ValueMatcher.MatchValues` (2026-10-11):** two values are equal when their JSON kinds are the same and their values are identical. Strings compare their decoded text and numbers their raw text, ordinal and case-sensitive, so nothing is trimmed, case-folded, Unicode-normalized or converted: `"Masoud"` does not equal `"masoud"`, `" Hello "` does not equal `"Hello"`, `123` does not equal `123.0`, `1e2` does not equal `100`, and a precomposed `é` does not equal `e` plus a combining accent. `true`, `false` and `null` each equal only themselves. Different JSON kinds never match, so `"123"` against `123` and `"true"` against `true` are not equal. Objects and arrays are not primitives and never match under this rule, whatever they hold. A `String` node without a `Value` (undecodable) equals nothing, itself and JSON `null` included: the absent text is not read as a null value. Lone surrogates are compared as the UTF-16 units they are, so identical malformed strings are equal and different ones are not. `Exact | Normalized` keeps the OR rule: a pair is equal when either rule accepts it, so with both set `"Masoud"` equals `"masoud"` and `123` equals `123`. `Normalized` is unchanged. Numbers are judged as written on purpose: `-0` against `0`, `1E2` against `1e2` and `1.0` against `1` are for `Numeric`, not `Exact`. No public API, no scoring and no call from `StructureMatcher` were added, and the fixtures were not extended: every scenario is covered by values the fixtures already hold (`normalizedValues`, `primitiveValues`, `loneSurrogates`, `loneSurrogateNames`, `meta.flags`, `quotedNames`, `duplicateKeys`, `customer`, `items[0].attributes.options`), with the undecodable string produced the way the `Traverse` tests do, by damaging the fixture's bytes in memory. Details are in `MatchValues.md`.
- **`Numeric` value matching is implemented, as a third rule of `ValueMatcher.MatchValues` (2026-10-11):** two numbers are equal when they denote one quantity, exactly and without tolerance: `123` equals `123.0`, `1e2` equals `100`, `-0` equals `0`, `1E+3` equals `1000.000`, `1.5` equals `1.50`; `9007199254740992` and `9007199254740993` differ, as do `1e100` and `1e101`, and `1e-100` is not `0`. No `double`, `float` or `decimal` is used: each raw text is reduced to its sign, significant digits without leading or trailing zeros, and a power of ten read into a `BigInteger`, and the three parts are compared. The digits stay text, so no precision is lost at any size; the exponent is exact within available resources. Nothing is raised to the represented power. Mantissa processing is linear, but `BigInteger` exponent conversion is runtime-dependent and not guaranteed linear; the former claim that no input is expensive was incorrect (review, 2026-10-12). Zero has no sign and no scale. The rule applies to two `Number` nodes only: nothing is coerced, so `"123"`, `true` and `null` never equal a number, and two identical strings, Booleans or nulls are not decided by it (`Exact` does). The raw texts on the nodes are unchanged, and `Exact` and `Normalized` are unchanged; the OR rule holds for `Exact | Normalized | Numeric`. A tolerance was considered and rejected: the mode is named for quantity equality, approximate equality would need a parameter, and nothing asks for one. The fixtures gained a `numericValues` section (below); the two complete-mapping expectations of the `Traverse` tests and the Stringified fixtures were updated for it. Details are in `MatchValues.md`.
- **`Fuzzy` value matching is implemented, as a fourth rule of `ValueMatcher.MatchValues` (2026-10-12):** two strings are equal when their folded texts are at most one edit apart for every five UTF-16 units of the longer one. Folding is the `Normalized` treatment (trim, NFC) followed by `ToUpperInvariant`, so case, padding and Unicode form are ignored before edits are counted; the distance is the optimal string alignment distance (insertions, deletions, substitutions and adjacent transpositions, each one edit); the threshold is five times the distance at most the longer length, a similarity of 0.8, held in the constant `FuzzyUnitsPerEdit`. `"Jon Smith"` equals `"John Smith"`, `"Smith"` equals `"Smyth"`, `"recieve"` equals `"receive"`; `"Jon"` does not equal `"John"`, nor `"Hélène"` `"Helene"`, nor `"John Smith"` `"Smith John"`. The rule applies to two strings only; nothing is coerced and no other kind is decided by it. The distance keeps three rows and stops once a row exceeds the allowance, after a length check that needs no table at all. This is a first working version: the measure, the threshold (and whether it should scale for short texts), accent folding, digits and the quadratic cost are to be reviewed, and no parameter is exposed. The fixtures gained a `fuzzyValues` section (below); the two complete-mapping expectations of the `Traverse` tests and the Stringified fixtures were updated for it. The stress documents are also run through `Fuzzy`, and that sweep found that `Normalize` let `string.Normalize` throw on a string holding U+FFFE or U+FFFF (the `noncharacters` string): `IsWellFormed` now treats those two as it treats a lone surrogate, so such a string is only trimmed under `Normalized` and `Fuzzy`. Details are in `MatchValues.md`.

## Known limitations

- **`Traverse` has no depth guard; very deep input is unsafe.** It recurses once per object or array level, as does the walk over its tree in `ExtractPropertyPaths`, and both rely on the parser's default `MaxDepth` of 64. If a caller raises `MaxDepth`, two things go wrong. A deep enough document ends in a stack overflow, which cannot be caught and ends the process. And because each ID repeats its whole parent path, the total length of the IDs grows with the square of the property depth; this affects only the `ExtractPropertyPaths` projection, since the tree stores no IDs. In a one-off measurement outside the test suite, taken before the tree existed (.NET 10, macOS, main thread), 20,000 nested objects completed but allocated about 764 MB, and 50,000 nested objects or arrays overflowed the stack at about 25,000 frames; a thread with a smaller stack overflows sooner. The stress tests raise `MaxDepth` to 128 and include a 100-level array, so the former statement that no caller raises it was incorrect. Those tests demonstrate traversal at that depth, not stack safety at arbitrary depth; a stack overflow would end the test host. Accepted as is; no guard has been added. Whatever parses input for `JJMatcher` must keep the default `MaxDepth` or add a guard first.
- **Extraction collisions.** The extracted dictionary cannot distinguish an object from an array holding it, duplicate keys from objects in an array, different groupings of the same elements in nested arrays, or different value types of one property. The details and the tests that pin them are in `ExtractPropertyPaths.md`. The `JsonStructureNode` tree keeps all of these cases distinct.
- **The tree is a full copy of the document.** One node per JSON value plus one string per name occurrence and per string or number value, several times the size of the UTF-8 text. Measured with `benchmarks/JJMatch.Benchmarks` (.NET 10, macOS, short job): `Traverse` allocates about 50 to 55 KB for each fixture of 5.5 to 5.9 KB, and `ExtractPropertyPaths` about 100 KB including that tree. Accepted as is.
- **Numbers are kept as written, not as quantities.** `1.0` and `1`, or `1.5E+10` and `15000000000`, are different `Value`s in the tree. Numeric equality is the `Numeric` value matching rule, which reads the written texts as quantities without changing them.

- **`StructureMatcher.Match` is not optimized** (superseded by the performance optimization above; the figures here are the ones it was measured against). Measured with `benchmarks/JJMatch.Benchmarks` (figures in `Match.md`). Time and memory grow with the square of a group's size because every pair is compared, identical shapes included since the whole group is assigned; assigning a whole group is O(n³) with an O(n⁴) worst case in its tie rule, and costs nothing measurable on top at any size measured. There is no bound on group size. Accepted for this version; see the decision above.
- **The lone surrogate fallback of `Traverse` is not optimized (known limitation, future optimization opportunity).** It is correct but slow, and only documents holding lone surrogate escapes pay for it: valid JSON takes the normal path, measured against the version without the fallback at 0 to 6% more time and no additional allocation (BenchmarkDotNet, .NET 10, Apple M5: `Left.json` without `loneSurrogates` 10.87 against 11.51 µs, 10,000 small objects 2.10 against 2.22 ms, one object of 10,000 properties 0.94 against 0.93 ms). The figures below are one-off stopwatch measurements outside the repository on the same machine, valid names against lone surrogate names of the same length, and are approximate. Nothing here was optimized or redesigned; accepted for this version under the correctness-first decision above.
  - *Exception-driven decoding.* A name or value is first decoded normally, and the fallback starts only when that throws, so every malformed name or value costs one thrown and caught `InvalidOperationException`, about 20 µs. An object of 10,000 properties takes 0.61 ms with valid names and 20.5 ms with lone surrogate names, about 30 times slower (1,000: 0.13 against 2.4 ms; 100,000: 9.2 against 215 ms); 10,000 lone surrogate string values take 20.0 ms against 0.55 ms. The cost is linear in the number of malformed strings, not quadratic. Detecting a lone surrogate without an exception would need the raw text of every name, which is what the normal path avoids.
  - *Repeated raw-text parsing.* An object with at least one undecodable name is read a second time, whole, to collect its raw names, once per object however many of its names are malformed. One lone surrogate name at the end of 10,000 valid ones takes 1.7 ms against 0.61 ms. The second read walks the whole subtree, nested values included, only to find the names at the top.
  - *Quadratic time with nested objects.* When objects with malformed names are nested, each level reads its whole subtree again, so the time grows with depth times size. At the parser's default `MaxDepth` of 64 the factor is bounded: 60 levels around 100,000 properties (1.1 MB) take 88 ms against 7.8 ms. When a caller raises `MaxDepth` it is not: a chain of 500, 1,000 and 2,000 such levels around a 1,000-property object (14 to 31 KB) takes 10.5, 24.4 and 69 ms, against 0.04, 0.06 and 0.12 ms with valid names.
  - *Increased allocations.* Each raw name is copied to a byte array, decoded to a string and unescaped through a `StringBuilder` into the final name, on top of the exception object: 10,000 lone surrogate names allocate 8.4 MB against 1.3 MB (100,000: 83 MB against 13 MB), and 10,000 lone surrogate values 7.9 MB against 1.3 MB; one lone surrogate name among 10,000 valid ones allocates 2.4 MB, because every raw name of the object is decoded, not only the malformed one. Before the names were read from the element's bytes, each second read also copied the whole object twice (a .NET string and its UTF-8 bytes), so nested levels allocated depth times size: 209 MB against 13 MB for the 60 levels around 1.1 MB above, now 13.3 MB. That part went away with the invalid UTF-8 fix; the rest is unchanged.
  - *Possible optimizations, none attempted:* collect only the name that failed instead of every name, skip nested values while collecting (`Utf8JsonReader.Skip`), decode from the bytes without the intermediate string and `StringBuilder`, or scan a name's raw bytes for a lone surrogate before decoding so that no exception is thrown.

## Open items

- How tests for `null` and malformed input at the `JJMatcher` level fit the fixture rule is undecided, since such input cannot live in a valid JSON file.
- Stringified JSON input handling is not implemented: no parsing or normalization exists. The `StructureMatcher` test treats their roots as plain strings; a separate fixture-integrity test now verifies that decoding each TXT yields the exact corresponding JSON text. Neither implements public input normalization.
- `StructureMatcher.Match` is not called by `JJMatcher.Match`, and how its result reaches `JJMatchResult` is undecided.
- No public method accepts a `JJArrayMatchingMode` yet (`JJMatcher.Match` takes only `JJMatchOptions`), so a mode cannot be selected; only the enum and its default exist. Adding the parameter changes the public API and is undecided.
- `JJMatchOptions.StructuralMatching` is described as scoring array lengths, while `StructureOnly`, the default mode, ignores element count. Which wins is undecided.
- No public method accepts a `JJValueMatchingMode` yet, for the same reason as `JJArrayMatchingMode` above. The default a public API gives an omitted mode must be `Exact`, not `None`.
